# GitHub 云端数据架构

## 定位

GitHub 作为版本化的云端备份与同步仓库，桌面端 SQLite 继续作为本地实时数据库。应用不直接在远程仓库中读写正在使用的 SQLite 文件，避免二进制冲突、网络中断损坏和频繁提交。

## 推荐结构

```text
cloud-data/
  manifest.json
  shops/
    {shop-id}/
      snapshots/
        2026-09-08T120000Z.db.zst.enc
      events/
        2026-09/{device-id}.ndjson.enc
      exports/
        experiments/2026-09/{experiment-id}.json.enc
        reports/2026-09/{report-id}.json.enc
  devices/
    {device-id}.json
```

- `manifest.json`：格式版本、最新快照、各设备同步游标、文件校验值和更新时间。
- `snapshots`：SQLite 一致性快照，压缩后加密，用于首次恢复和灾难恢复。
- `events`：新增、修改、删除操作的追加式事件；每条包含全局事件 ID、店铺、实体、实体 ID、版本、设备和时间。
- `exports`：广告实验、系列报告等可审计 JSON。缺失值仍为 `null`，保留数据质量字段。
- `devices`：设备标识及最后确认的同步位置，不保存访问令牌。

## 同步流程

1. 应用通过 SQLite backup API 生成一致性本地快照，不复制正在写入的数据库文件。
2. 本地业务写入同时记录 outbox 事件，使用 UUID 保证重复上传不会重复应用。
3. 同步前读取远端 `manifest.json` 及其提交版本，下载尚未应用的设备事件。
4. 在单个本地事务中按实体版本合并；删除使用 tombstone，不直接抹除历史。
5. 上传本机事件和必要的新快照，再以远端提交版本作为条件更新 manifest。
6. 如果 manifest 已被其他设备更新，重新拉取、合并后重试，禁止强制覆盖。

## 冲突规则

- Ozon 同步所得事实数据按业务唯一键幂等合并，例如 `shop + day + campaign + sku`。
- 用户配置、商品成本和实验配置使用实体版本；并发修改保留冲突副本，要求用户选择。
- 广告实验基准快照一旦启动不可覆盖；事件、评分和决策只追加。
- 凭据、API Token、AI Key、Ozon Client-Id/Api-Key 永不进入仓库。

## 安全

- 使用私有仓库和仅限该仓库内容读写权限的细粒度 Token。
- Token 继续使用 Windows DPAPI 存储；数据包在上传前使用独立数据密钥加密。
- 数据密钥由用户恢复口令派生或放入系统凭据存储，不写入仓库。
- 每个数据包保存 SHA-256，恢复前先校验；恢复动作先自动备份当前本地库。

## 产品界面

在“数据与协作”下增加“GitHub 云同步”：

- 连接设置：仓库地址、分支、Token、加密恢复口令。
- 状态卡：最后上传、最后下载、待上传事件、远端最新版本、冲突数。
- 操作：立即同步、仅备份、查看版本、从快照恢复、断开连接。
- 首次启用先创建加密快照并展示文件清单；恢复前展示来源时间、店铺和校验结果。

## 分阶段实现

1. 第一阶段：手动加密快照上传、快照列表和恢复验证。
2. 第二阶段：outbox 增量事件、自动同步、断网续传和幂等合并。
3. 第三阶段：多设备冲突中心、历史版本对比和选择性恢复。

第一阶段可以快速提供可靠云备份；确认恢复链路稳定后再开放多设备双向同步。
