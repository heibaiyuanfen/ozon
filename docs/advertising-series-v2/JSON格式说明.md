# 产品系列广告 JSON：第一版格式提案

本目录中的 ABC JSON 文件是供评审的模拟样稿，不是店铺经营结果。2026-09-07 已按此格式接入功能代码，正式导出 schemaVersion 为 2.1、isSample 为 false；发布及验收结果见项目架构日志。

## 操作设计

勾选产品 A、B、C → 输入系列名称并保存（也可临时组合）→ 选择最近 7 天、最近 30 天、自然月或自定义起止日期 → 预览 → 导出 JSON。
最近 7/30 天默认截止昨日，允许修改截止日期；自然月按实际天数，不等同于 30 天。起止日期均包含。修改产品或日期后须重新生成预览，确保文件和当前选择一致。

## 固定层级

| 字段 | 内容 |
|---|---|
| schema / schemaVersion | 格式标识及版本 |
| isSample | 是否模拟样稿；正式数据必须为 false |
| shop / currency / period | 店铺、币种、日期范围及来源日期口径 |
| series | 系列名称、唯一 SKU 列表及成员数量，保存本次选择快照 |
| products[] | A、B、C 各自独立对象：商品信息、daily 每日明细、summary 周期合计 |
| seriesDaily[] | 每天 A+B+C 的销量、销售额、广告数据合计 |
| seriesSummary | 整个期限内 A+B+C 的总计 |
| metricDefinitions / formulas / dataRules | 字段解释、固定公式、缺失及汇总规则 |

每个 daily 行和 summary 对象使用同一套指标名称。7 天样稿包含 3 个产品各 7 行，加上系列每日 7 行；自然月样稿包含各 30 行（2026 年 8 月则应为 31 行）。不省略无销售日期。

## 指标口径

- totalUnits：全部下单销量（件），对应当前 sales_daily.ordered_units，不是订单数，也不代表扣除退款后的净销量。
- totalRevenue：销售数据源中的全部销售额。正式导出需要明确源报表口径，不能擅自标记为净收入。
- impressions、clicks、adOrders：广告曝光、点击、归因订单数。
- spend、adRevenue：广告费用、广告归因销售额，统一使用文件声明的币种。
- ctr、conversionRate、acos、tacos：百分数数值，例如 5 表示 5%，不是 0.05。
- cpc、cpa：每次点击/每个广告归因订单的广告成本；roas 是倍数。
- salesStatus / advertisingStatus：complete、partial、missing，分别标记两类数据的完整性。样稿均为 complete。

广告订单不等于广告销量。不能用 totalUnits - adOrders 推算自然销量。广告归因日和销售下单日不一定一致，不要求广告销售额每天小于全部销售额。

## 汇总与缺失规则

1. 产品周期合计 = 该 SKU 各日基础指标之和。
2. 系列每日合计 = 所选 SKU 同一天基础指标之和；去重 SKU，限制在同一店铺内。
3. 系列周期合计 = 系列各日基础指标之和，同时必须等于各产品周期合计之和。
4. 所有比率先汇总分子和分母再计算，禁止平均每日或单品比率。公式见 JSON 的 formulas。
5. 分母为 0 或任一输入缺失时，比率为 null。基础指标只有经确认完整且无业务时才为 0；未采集为 null，不伪装成零。
6. 基础指标合计只累加已知值，全部未知才为 null；missingMetrics 标注哪些合计仍有缺失。任一分子或分母缺失时不计算比率。dataQuality.missingData 列出日期、产品 SKU/货号及缺失指标。
7. 店铺级无法分配到 SKU 的广告费用不分摊，不混入该系列；正式导出应附质量说明。跨广告数据源先去重，避免重复计费。
8. 使用源报表日期，不凭电脑时区重切日期。正式导出填写已核验的时区；未知时区为 null 并给出说明。
9. 金额在原始精度汇总后输出两位小数；百分数与倍数输出四位小数。不能累加已经四舍五入的比率。

## 实现说明（2026-09-07）

已实现单品逐日、单品周期、系列逐日和系列周期四层结构；产品候选来自商品、销售和广告数据的 SKU 并集，不再仅限有广告的产品。支持 7 天、30 天、自然月和自选 1～366 天，最多 500 个 SKU。修改选择、名称或期限后旧预览不允许导出，计算中的过期响应不会覆盖当前选择。

现有数据库没有逐日逐 SKU 的同步完成凭证，因此实际导出中有记录标记 partial（已采集值但未保证完整），无记录标记 missing，尚不能可靠输出 complete。部分日缺失时显示已知周期合计并用 * 标明不完整；关联比率为 null。日明细与缺失清单保留可核查范围。此限制在界面和 JSON dataQuality 中明确告知。示例文件的 complete 仅用于模拟完整数据场景。

销售和广告金额使用同一币种；跨境店铺按当前配置汇率从 RUB 换算 CNY，并附 currencyConversion，非历史每日汇率。导出采用只读数据库事务保持本次快照一致。文件保存到应用现有 exports 目录，成功后界面显示完整路径；文件名带店铺标识、日期范围与时间戳。


## 2.1 修复说明

- 历史报表各指标独立解析，缺失、空值、非数值不再填成零。日期/计划无法匹配的行跳过，不阻断其他有效行；日志提示校验与部分字段情况。
- 为兼容旧模块 ad_daily 的 NOT NULL 约束，新建 ad_partial_daily 保存部分字段记录；系列面板优先读取同键最新部分记录并排除重复旧记录。完整报告写回原表并清除对应部分记录；旧页面仍使用原有完整记录，部分字段的新数据通过本系列面板查看。
- JSON 版本升为 2.1，基础指标为已知合计（aggregationBasis=known_values_only），missingMetrics 和 dataQuality.missingData 给出完整性限制。旧版本样稿仅供结构参考。
- 同步部分失败后仍刷新已保存数据预览，保留错误说明；切换产品或店铺后忽略过期响应。


### 同键多行的部分字段合并
同一日期/计划/SKU 的多条明细先累加已知字段，missing_mask 单独保留未知片段的标记。即使累计出了已知订单数，仍会通过 missingMetrics 标记为不完整，CPA/转化率不会据此错误计算。重试使用 UPSERT 替换该批合计，不重复累加历史记录。同步日志随已保存批次累计行数，后续失败也不再显示零行。
